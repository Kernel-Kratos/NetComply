02 / Architecture

Separate understanding from judging.

Interpreting vendor syntax is messy, so Gemma 4 does it. The verdict has to be consistent and auditable, so deterministic rules decide it. Orange marks where Gemma 4 is involved. Everything else is deterministic.

1

Ingest & preprocess

Single or bulk upload. Detect vendor and OS, split into blocks, redact secrets (hashes, keys, SNMP strings).

↓
2

Normalize Gemma 4

(a) learned-mapping lookup → (b) Gemma returns field, value, source_line, confidence → (c) low-confidence lines to the review queue. Evidence that isn't in the input is rejected.

↓
3

Security Baseline Model

One vendor-neutral JSON per device. null = not found, false = explicitly disabled.

↓
4

Compliance engine

YAML rules with a closed set of operators. Pass / Fail / Unknown plus severity and framework references.

↓
5

Remediation Gemma 4

Vendor templates first, Gemma for gaps. CLI in the device's own syntax, labeled “Suggested. Review and test before applying.”

↓
6

PDF report

One per device. Same input, same report.

↺ Training loop

  1. Unrecognized lines land in the review queue
  2. Gemma suggests a control (shown as a suggestion)
  3. Admin accepts, edits or skips
  4. Mapping saved to the store
  5. Re-audit: step 2a now matches it directly

Why Gemma 4

The right model for configs.

01

Reasoning

Interprets syntax it hasn't seen before and maps it to security controls.

02

Agentic workflows

Suggests mappings and drafts vendor-specific fixes inside a validate-and-retry loop.

03

Open weights

Can run on a laptop or an on-prem server, so configs with IPs and topology stay in the building.

04

One switch

Mock, local, LAN or hosted. Changing the backend is a .env edit, with no code changes.
